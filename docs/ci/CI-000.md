# CI-000：个人维护与 Docker 手动发布

当前流程按维护者 2026-10-12 的要求简化：开发反馈只运行路径相关 Quick；准备发布时手动运行一次固定源码的 Full，再手动构建发布 Linux amd64 镜像。不要求 PR 自动 Full、合并后自动 Full、严格 main/personal 分支保护或多人批准。旧流程的历史验收保留在 [CI-000-ROLLOUT.md](CI-000-ROLLOUT.md)，其中自动触发与合并复用规则不再适用于当前流程。

## 入口

| 入口 | 执行内容 | 是否发布 |
|---|---|---|
| 普通 PR 更新 | 路径相关 Quick；依赖变化保留对应审计 | 否 |
| Ready / full-ci 标签 | 不额外触发 CI | 否 |
| personal push | 路径相关 Quick | 否 |
| 上游同步机器人 | 自动 PR 仅绑定检查；显式 dispatch 路径相关 Quick | 否 |
| 手动 Personal CI quick | 固定候选、基础与 PR 的路径相关检查 | 否 |
| 手动 Personal CI full | 原有完整检查及结果认证 | 否 |
| 手动 Personal release | 检查固定 SHA 的成功手动 Full，分配版本并调度 Release | 是 |
| 手动 Release dry-run | 构建并验证所选产物，不写 registry 或 Release | 否 |
| 周扫 / 手动安全扫描 | 保留既有依赖审计和固定工具版本 | 否 |

推送版本标签不再触发 Release，Personal CI 完成也不再触发 Personal release。上游同步的计划开关独立于发布，不会把同步候选自动上线。

## 发布操作

首次使用前，将本次控制改动合入 main，并只把对应 `.github` 控制文件同步到 personal；不要合并 main 的应用树。personal 的必要文件包括 personal-ci.yml、backend-ci.yml、personal-release.yml、release.yml、sync-upstream.yml、ci_policy.py、sync.py、personal_release.py 及相关合同测试，保留已有配套工具。实际应用构建来自 personal，正式发布控制工具来自同次 main 快照。

1. 完成应用修改，按改动运行相关本地检查并更新 personal。PR 是审查和记录方式，可按任务需要使用；它本身不是 Docker 上线的技术前置。
2. 在 Actions 的 Personal CI 页面选择 personal，mode 选择 full，candidate_sha 和 base_sha 都填写当前 personal 完整 SHA，pr_number 留空。也可以使用：

   ```bash
   release_source_sha=$(gh api repos/ccisnoxx/sub2api/branches/personal --jq .commit.sha)
   gh workflow run personal-ci.yml --repo ccisnoxx/sub2api --ref personal \
     -f mode=full -f candidate_sha="$release_source_sha" -f base_sha="$release_source_sha"
   ```

3. 等该次运行全部成功后，在 Personal release 页面选择 main，source_sha 填写相同 SHA，ci_run_id 填写该运行 ID；留空时只查找该 SHA 的有效手动 Full。发布开关 `PERSONAL_RELEASE_ENABLED=true` 保留，默认未开启时不执行发布。

   ```bash
   gh workflow run personal-release.yml --repo ccisnoxx/sub2api --ref main \
     -f source_sha="$release_source_sha"
   ```

4. 等 Release 完成，再使用明确版本或 digest 手动部署。发布工作流不访问生产主机。部署备份、健康验收和迁移兼容规则见 [个人部署工具](../../deploy/personal/README.md)。

Full 保留后端 unit/integration、recording Race、lint、部署和发布工具合同、同步合同、安全扫描、前端关键测试与构建。完整检查集中在发布候选；开发时根据实际边界选择相关检查，不因路径的风险标记自动升级 Full。现有扫描等级和审计例外保持。source SHA 未变且已绑定运行仍有效时，发布重试复用该成功记录，不重新调度检查。

## 发布绑定与失败处理

personal-ready 聚合本次选中的 job：必要 job 必须 success；未选中的 job 可以 skipped，失败、取消和缺失均不能通过。full-ci-certified 仅认证手动 Full，并验证本次所有必要 job；Quick 不要求这个 marker。

发布工具直接读取固定 CI run 的实际 jobs，验证 workflow ID/path、仓库、personal 分支、完整 source/base SHA、手动 Full 标题和成功完成状态。必要 job 必须在同一次运行中全部成功；不查询分支保护或其他提交的 check-runs，不复用 PR、push、merge tree 或另一运行的部分成功结果。当前 personal 已变化、Quick、旧自动 Full、失效或重跑失败记录均拒绝发布。

prepare 选定的 run ID 在发布全过程保持固定，标签、源码和镜像 revision/digest 继续绑定，写入前再次检查。已有正确版本允许恢复部分发布，错误占用禁止覆盖。移除分支保护依赖不取消来源、祖先、不可覆盖版本或备份规则。main/personal 可以配置禁止强推和删除等基础保护，但严格 required checks、多名审批或合并队列不是上线前置。

## 验证与回退

本次修改只涉及 CI/发布控制工具和维护文档，数据库影响为 none。使用现有固定 CPython/PyYAML 的同步与发布合同测试，以及 actionlint 检查改动的 workflow；不因调整触发器运行应用全量回归、云端发布或生产部署。具体结果以本次交付记录为准，不能把旧 rollout 当作新配置的云端验收。

回退使用普通 revert，同时恢复生产者与消费者的工作流、分类规则、同步调度和发布 gate，并同步必要控制文件到 personal。保留已有 tag/SHA/digest，不强推、移动正式标签或覆盖镜像。GitHub 外部保护规则如另行修改，须单独恢复；修改仓库文件不会改变现网设置。
