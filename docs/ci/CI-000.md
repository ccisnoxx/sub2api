## 触发与门禁

| 入口 | 检查 | 合并/发布要求 |
|---|---|---|
| 普通 PR 更新 | 路径相关 Quick | 低风险 personal-ready 可通过 |
| 高风险 PR 更新 | Quick；缺 Full 时 personal-ready 失败并提示入口 | 最终候选须 Full |
| Ready / 添加 full-ci 标签 | 一次 Full；同候选/基础成功时复用 | 纯文档 Ready 保持 Quick |
| 手动 Personal CI | 默认 Full，可显式 quick | 候选、基础和 PR 仍强绑定 |
| personal push | 文档 Quick；应用 Full；匹配已测试 merge 则复用 | 发布还须 full-ci-certified |
| 依赖 PR | 按 Go/前端依赖范围审计 | 扫描失败仍阻断 |
| 周扫 / 手动安全扫描 | personal 的 Go 与前端审计 | 保留固定工具版本 |

普通任务通常 PR Quick → 合并后一次 Full。高风险任务通常 PR Quick → 最终候选 Full → 合并复用。已完成 Full 的普通候选也可复用，避免 Ready/标签触发 Full 后合并又跑一次。上游同步与 `codex/verify-personal-ci-*` 专用候选仅由显式 dispatch 执行测试；自动 PR 入口始终执行绑定与证据门禁，缺少同 candidate/base 的成功 Full 会失败，绝不把 skipped 当作 required check 成功。run-name 显式记录 request full/quick/auto；同步脚本显式传 mode=full，仅复用 request full 的运行中 dispatch，并核对成功运行的真实完整 job 清单，旧 Quick 成功不能被误用。

backend-ci.yml 保留单一实现，通过 mode 和分类计划控制执行。自动 CI 仅监听 PR，移除功能分支 push 与 PR 双触发；main 控制任务可手动选择 Full。Security Scan 的普通 PR 入口仅监听四个依赖文件；govulncheck 保留 v1.9.0，pnpm、Node、Python、Go 和 Action SHA 沿用 CI-001/002 固定政策。CLA 只保留手动入口和上游参考实现。

Full 保留后端完整 unit/integration、recording Race、全库 lint、部署脚本、发布工具、同步合同、安全扫描以及前端关键测试和构建。TPS 专项迁入同一个前端 job，前端普通检查与 TPS 只安装一次依赖；未绑定 personal 且未包含 TPS 模块的 main 源码明确判定专项不适用，但仍构建前端；绑定 personal 时模块缺失不得跳过。安全审计使用独立隔离 job。专用分支所有自动 PR 事件进入 Quick 并发组，Ready/标签不会取消其显式 Full。Quick 后端使用受影响包的现有 unit 分批入口、go vet 和编译；前端使用受影响文件 ESLint、typecheck 和 Vitest related。无相关测试时保留 typecheck/lint，Full 仍跑关键测试。文档仅校验 LICENSE/NOTICE 和变更 Markdown 本地链接，不做外部网络链接扫描。

分类基于本地完整 Git diff，并禁用 rename 检测以同时检查删除与新增路径。backend 内的运行 Markdown 不算文档；迁移、repository、handler/API、ent、server/middleware、认证/会话/API key、计费/支付/订阅/价格、gateway/scheduler/failover、Redis/并发/WS、前端 API/types、构建配置、依赖、部署及工作流均强制 Full。运行文件默认高风险；目前低风险清单仅包括 pagination.go/对应单测及 HelpTooltip.vue/对应单测。user/account/group/config、前端管理用户与凭据构造无需命中关键词也要求 Full。扩充低风险清单必须先确认实际所有权和合同，不允许新路径因未命中关键词自动绕过。

## Full 证据与发布

personal-ready 对选中的 job 要求 success，对未选中的 job 允许 skipped；失败、取消和缺失不算成功。高风险 Quick 可以提供测试反馈，但缺少 Full 时不会成为可合并结果。认证阶段重新查询当前证据，Quick 开始后刚完成的同 candidate/base Full 也可以被接受；已固定但失效的证据不被静默替换。绑定检查在开始和结束均核对最新 personal、PR head/base、checkout 和上游祖先。

Full 证据查询验证 workflow ID/path、运行仓库和源码仓库、完整 candidate/base SHA、运行状态，以及所有 Full job 的实际成功状态。完整证据标记为 full-ci-certified。检查名称仍只需 personal-ready 作为分支保护的 required check；full-ci-certified 用于发布工具辨别完整证据。

合并复用仅支持两个父提交的普通 merge：第一父提交等于 push.before，第二父提交包含该基础，合并 tree 与第二父提交 tree 相同，并存在该 candidate/base 的完整成功检查。squash/rebase、基础推进、冲突解决、合并时内容变化或失败/取消记录均重新 Full。复用时重新查询证据，不沿用失效状态；不跨发布源码 SHA 直接授权发布。最终 personal push 的运行再次完成绑定与聚合，并认证 tree 对应的完整证据。

发布工具继续验证当前 personal 完整 SHA、同一成功运行及 check suite、上游来源、保护规则和镜像 revision/digest，同时要求该次运行有成功 full-ci-certified，并由可信 main 工具重新读取最新 Full job 集合；同最终 SHA 的复用运行先重新核对 source=base=SHA 的真实 Full；合并复用则重新核对 merge 父提交/tree 及原始 candidate/base Full。原始 Full 被删除、重跑失败或必要 job skipped 时拒绝发布。自动查找会跳过较新的 Quick，继续寻找仍有效的 Full。旧版本工作流的笼统 success 不再满足新门禁；切换后须在最终 personal SHA 取得新 Full。自动 Personal release 对 Quick 完成记录只读检查后跳过版本分配；手动发布缺 Full 则明确拒绝。

GitHub 的 skipped/needs 传播和真实 workflow job 状态分别按[官方工作流语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)和[Jobs API](https://docs.github.com/en/rest/actions/workflow-jobs)核对。

## 落地、风险与回滚

1. main 控制面候选完成本地定向验证与独立复核，再一次推送 PR；不为中间提交重复 Full。
2. 合入 main 前完成控制面 CI；不修改分支保护或扩大审计例外。
3. 只同步必要的 .github 控制增量到最新 personal，包含新的分类/检查脚本与发布证据门禁；不能把 main 应用树合入 personal。首次同步是高风险候选，明确运行新 Full，并核对实际 job 名称/API、标签/Ready/dispatch、取消、文档跳过和合并复用。
4. 新规则落地后记录至少十个独立任务，核对文档约三分钟、小任务首次反馈十分钟内、普通任务一次 Full、无重复 Full、周扫保留以及发布拒绝 Quick。历史数据不能替代这组上线后验收。

风险：低风险清单初期保守，普通应用变更仍只在最终边界升级；Go service/handler 是大包，Quick 仍可能受包编译影响，耗时目标须实测。当前不支持 merge queue、squash 或跨 tree 复用；它们执行 Full。Quick 的相关测试不是完整回归证据。网络/API 或扫描服务故障显式失败，日志按失败步骤分类，不自动重试所有 job。

数据库影响：none。回滚：普通 revert 本任务控制提交并同步对应控制文件到 personal；分类脚本、workflow 输入和发布证据门禁必须一起恢复，避免接口不匹配。不得保留放宽后的发布检查，也不需要回退 schema、改标签或重部署生产。
