# CI-000：个人维护与 Docker 手动发布

当前流程按维护者 2026-10-19 的要求简化：日常开发按任务批次执行本地定向检查，云端 Quick 仅按需手动触发；准备发布时手动运行一次固定候选的 Full，普通同树 merge 后直接复用，再手动构建发布 Linux amd64 镜像。不要求 PR 自动 Full、合并后自动 Full、严格 main/personal 分支保护或多人批准。旧流程的历史验收保留在 [CI-000-ROLLOUT.md](CI-000-ROLLOUT.md)，其自动触发和旧认证机制不适用于当前流程。

## 入口

| 入口 | 执行内容 | 是否发布 |
|---|---|---|
| 普通 push / PR 更新 | 不运行应用 CI 或安全扫描 | 否 |
| Ready / full-ci 标签 | 不额外触发 CI | 否 |
| 上游同步机器人 | 仅准备候选 PR；手动选择 CI 演练才调度 Quick | 否 |
| 手动 Personal CI quick | 固定候选、基础与 PR 的路径相关检查 | 否 |
| 手动 Personal CI full | 原有完整检查及结果认证 | 否 |
| 手动 Personal release | 检查最终 SHA 或已合并同树候选的成功手动 Full，分配版本并调度 Release | 是 |
| 手动 Release dry-run | 构建并验证所选产物，不写 registry 或 Release | 否 |
| 手动 Release recovery verification | 只读核验原成功产物、固定镜像和运输绑定 | 否 |
| 明确的本机 publish-local 恢复 | 使用同一 main 控制版本和现有维护者认证完成发布 | 是 |
| 月扫 / 手动安全扫描 | 保留既有依赖审计和固定工具版本；每月 1 日 03:00 UTC | 否 |
| main 部署工具路径 push | 既有五分钟部署工具合同检查 | 否 |

推送版本标签不再触发 Release，Personal CI 完成也不再触发 Personal release。上游同步的计划开关独立于发布，不会把同步候选自动上线。

## 发布操作

将控制改动更新至 main，并只把对应 `.github` 控制文件同步到 personal；不要合并 main 的应用树。personal 的必要文件包括 personal-ci.yml、backend-ci.yml、personal-release.yml、release.yml、sync-upstream.yml、ci_policy.py、sync.py、personal_release.py 及相关合同测试，保留已有配套工具。实际应用构建来自 personal，正式发布控制工具来自同次 main 快照。

1. 追更上游时使用 Sync KlN into personal 准备升级 PR，解决冲突并完成必要控制/兼容合同和定向检查。Quick 只供开发反馈，不是 Full 的前置。稳定后固定 PR head 和当前 personal base，后续不再修改候选。
2. 在升级 PR 分支上手动运行一次 Full。以下命令从实际 PR 读取绑定，避免手抄 SHA：

   ```bash
   pr_number=<本次升级PR编号>
   candidate_sha=$(gh api "repos/ccisnoxx/sub2api/pulls/$pr_number" --jq .head.sha)
   base_sha=$(gh api repos/ccisnoxx/sub2api/branches/personal --jq .commit.sha)
   candidate_branch=$(gh api "repos/ccisnoxx/sub2api/pulls/$pr_number" --jq .head.ref)
   gh workflow run personal-ci.yml --repo ccisnoxx/sub2api --ref "$candidate_branch" \
     -f mode=full -f candidate_sha="$candidate_sha" -f base_sha="$base_sha" -f pr_number="$pr_number"
   ```

3. Full 全部成功且复核完成后，以 **merge commit** 合并 PR（不用 squash/rebase）。不再为仅 SHA 改变的同树合并调度第二次 Full。基础已变化、冲突解决或任何文件/模式/类型改变时，更新候选后重新检查；不能借用旧结果。
4. 在 Personal release 页面选择 main，source_sha 填写合并后的当前 personal SHA。ci_run_id 可留空自动查找，或显式填写刚才的 Full run ID。门禁优先查找最终 SHA 的有效 Full，没有时只查找该普通同树 merge 对应的候选 Full。发布开关 `PERSONAL_RELEASE_ENABLED=true` 保留，默认未开启时不执行发布。

   ```bash
   release_source_sha=$(gh api repos/ccisnoxx/sub2api/branches/personal --jq .commit.sha)
   gh workflow run personal-release.yml --repo ccisnoxx/sub2api --ref main \
     -f source_sha="$release_source_sha"
   ```

5. 等 Release 完成并核对正式版本、最终 source SHA 和 OCI digest，再按[hostdzire 精简上线顺序](../../deploy/personal/README.md#日常追更与上线顺序)手动部署。发布工作流不访问生产主机；新上游的迁移/运行树兼容审查、隔离验证、启动前备份和现场验收仍需完成。

直接更新 personal、没有 PR 或不满足同树复用条件时，在 Personal CI 选择 personal，`candidate_sha=base_sha=当前 personal 完整 SHA`，`pr_number` 留空，运行一次 Full，再执行第 4—5 步。不需要先在 PR 和合并后各跑一次。

Full 保留后端 unit/integration、recording Race、lint、部署和发布工具合同、同步合同、安全扫描、前端关键测试与构建。完整检查集中在发布候选；开发时根据实际边界选择相关检查，不因路径的风险标记自动升级 Full。数据库迁移、计费、权限、并发等变化仍须选择直接覆盖实际合同的定向检查，不推迟到首次生产使用。现有扫描等级和审计例外保持。source SHA 未变且已绑定运行仍有效时，发布重试复用该成功记录，不重新调度检查。

## 发布绑定与失败处理

personal-ready 聚合本次选中的 job：必要 job 必须 success；未选中的 job 可以 skipped，失败、取消和缺失均不能通过。full-ci-certified 仅认证手动 Full，并验证本次所有必要 job；Quick 不要求这个 marker。

发布工具直接读取固定 CI run 的实际 jobs，验证 workflow ID/path、仓库、精确分支、完整 candidate/base SHA、手动 Full 标题和成功完成状态。必要 job 必须在同一次运行中全部成功，不拼接另一运行的部分成功结果。

同树复用额外要求：当前 personal 正好是 GitHub 记录的同仓库已合并 PR 的 merge commit；恰好两个父提交，第一父等于检查时的基础，第二父等于已检查的 PR head，且候选包含基础；最终提交与候选的**完整 Git root tree 相等**。这同时覆盖应用、依赖、CI/workflow、文档、文件模式和类型。PR 的 base 仓库/分支/SHA、head 仓库/SHA/分支必须一致；不依赖候选分支仍存在。squash/rebase、无关同树提交、合并后追加提交、变化的基础或树都不能借用此结果。API 查询失败明确停止；元数据不满足时须使用最终 SHA 的 Full。

不查询分支保护或其他提交的 check-runs，不接受 pull_request/push 自动检查、Quick、旧自动 Full、失效或重跑失败记录。检查开始与结束仍核对候选和当前基础；发布仍验证最终 checkout、当前 personal、上游标签及祖先，最终源码身份不会替换成候选 SHA。prepare 输出 `ci_source_sha` 与 `ci_reused`，区分被检查提交和实际发布提交。

prepare 选定的 run ID 在发布全过程保持固定，标签、源码和镜像 revision/digest 继续绑定，写入前再次检查。已有正确版本允许恢复部分发布，错误占用禁止覆盖。移除分支保护依赖不取消来源、祖先、不可覆盖版本或备份规则。main/personal 仅禁止强推和删除，允许维护者直接提交，不要求 PR、required checks、多名审批或合并队列。管理员也遵守这两项防误操作约束。

## 已构建产物的恢复

原 simple Release 仅发布 job 失败、成功构建与固定版本镜像仍在时，使用 main 的 `release-recovery.yml` 只读验证原 run、artifact、source SHA、tag、成功 Full 和 OCI 主 digest。验证不会重建应用、执行旧 artifact 中的工具或重跑 Full；Simple 原合同只发布 GHCR 镜像及证明，不上传二进制下载包。

验证成功后，从原 source checkout 运行同一已提交 main 控制版本的 `release_recovery.py publish-local`，显式选择 `--auth gh-maintainer`。入口使用本机既有维护者认证，绑定 verification run/attempt、artifact digest、原 producer 和当前 main 文件字节，再核验原 source/Full/tag/digest。云端 GITHUB_TOKEN 不承担该写入；本机 publisher 记录真实方法与维护者身份。该流程需要现有认证的 repo/workflow/write:packages 权限，不新增凭据或伪造 Actions 环境。

受控 draft 通过维护者可见的分页列表发现，同名资产只在 size/digest 完全相同时复用，冲突不覆盖。所有未完成 Personal release 及同 source 的 Release 均阻断写入；跨 GitHub/registry 无原子事务，最后一次检查后的新并发仍可能留下部分状态。原 tag/SHA/digest 保持不变，先完成恢复，再同步控制修改到 personal；不能在恢复前改变 personal SHA。实际验收及命令参数见 [发布工具](../../.github/release-tools/README.md) 和本次发布记录。

## 验证与回退

本次修改只涉及 CI/发布控制工具和维护文档，数据库影响为 none。使用现有固定 CPython/PyYAML 的同步与发布合同测试，以及 actionlint 检查改动的 workflow；不因调整触发器运行应用全量回归、云端发布或生产部署。具体结果以本次交付记录为准，不能把旧 rollout 当作新配置的云端验收。

回退使用普通 revert，同时恢复生产者与消费者的工作流、分类规则、同步调度和发布 gate，并同步必要控制文件到 personal。保留已有 tag/SHA/digest，不强推、移动正式标签或覆盖镜像。GitHub 外部保护规则需单独恢复；更新代码不会恢复远端设置。禁止直接回退至监听 push 的旧发布工作流，恢复前必须关闭发布开关并评估自动触发。
