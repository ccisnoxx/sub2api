## 二进制 SBOM 与来源

每个构建目标先核对实际归档和原矩阵 manifest，再从归档提取唯一应用二进制。固定 Syft 1.54.1 扫描二进制 Go module build info，以及同一源码的 frontend package.json/pnpm-lock.yaml，输出 SPDX 2.3 JSON。SBOM 登记实际 Go 二进制依赖和前端锁定的完整构建依赖；锁文件包含开发依赖，不声称所有 npm 条目均进入运行时 bundle，也不把清单当成完整许可证文本。

每份归档另生成未签名 in-toto Statement v1 / SLSA provenance v1。subject 绑定归档和 SBOM 的实际 SHA-256；记录精确 source SHA、版本、目标、工具工作流 SHA、Actions run URL、成功 CI run ID（正式发布）、实际工具版本及白名单输入摘要。消费端核对完整目标矩阵、归档/SBOM 哈希、源码、工作流及 run，不允许缺失、额外或错配材料。

工具安装只允许 `supply-chain-tools.json` 中登记的官方 Linux amd64/macOS arm64 归档 SHA-256。Syft 1.54.1 与 ORAS 1.3.4 的 release asset digest 已通过官方 GitHub API 核对，安装后再检查实际版本；不安装 latest、不回退到其他版本，也不新增长期 secrets。新平台或升级须独立 PR 核对官方版本、哈希和 release notes。

## OCI 证明与发布顺序

BuildKit 使用固定 scanner index `docker/buildkit-syft-scanner:1@sha256:ae4f3b554449e7e25548e7d8ccc029d17357348e30c6e3df01b92bc93654d6a9`，生成 SPDX 和 `mode=max` 原生 provenance。镜像配置明确写入 `source`、完整 `revision`、`version`、UTC `created`。

所有镜像先以明确的镜像名导出 OCI tar；`--tag` 只命名本地输出，不发布。BuildKit v0.34.0 根据 ImageName 生成原生 in-toto subjects，缺少名称会得到空 subject，因此必须显式命名并继续拒绝空 subject。校验器核对根索引、manifest/config/layer 的实际 digest 和 size、运行平台与 config 的一致性、每个平台的标签、证明关联 descriptor、in-toto subject，以及 SPDX/provenance 是否齐全。证明通过后才进入既有发布授权门禁。ORAS 复制内容寻址的完整索引，保留关联证明；不经会丢弃证明的默认 Docker image store。正式发布从 registry 的精确 digest 重新拉取并核对，再补齐 latest；full 模式另核对 amd64/arm64 合成矩阵。

已有版本恢复只读取和校验，不覆盖版本或重新构建。原有镜像若缺少本任务要求的证明，将明确失败，维护者应采用新的源码/版本候选完成发布，不能替旧版本编造证明。恢复时沿用已经发布镜像的 UTC created；不能要求它等于重试 run 的新构建时间。

## 运输、Release 与验证边界

所有证明附件名称绑定 Release run ID 与 attempt，包括 summary 和 checksum 清单；同一 run 重跑可追加本次材料而不与上一轮部分上传的资产冲突，不替换或删除旧尝试。GoReleaser 使用 append 模式，在恢复已有 draft 时保留旧说明并追加本次完整材料的 run/attempt 前缀与 summary，避免成功重跑仍只引用首个失败 run。二进制 SBOM 的逻辑文件名同时写入对应 provenance subject。只重跑失败 Release job 时，保留成功 binary job 原生产 attempt 的证明，不虚构重建；运输附件加上当前 attempt 前缀避免同名冲突，summary 登记逻辑名、公开名和相同内容哈希，消费者可按映射校验原始 subject。

正式 Release 附件包含二进制 SBOM/provenance、镜像纯 SPDX 文档与其原生 in-toto SBOM statement、BuildKit/pipeline provenance、verification、release summary 和 SHA-256 清单。simple 模式仍不上传应用二进制，但会上传上述证明附件。Release notes 包含 source SHA、成功 CI run、Release run 以及验证后的镜像 digest/平台。

每次 run/attempt 使用独立名称上传 supply-chain artifact，采用固定的不可覆盖 upload-artifact v7，保留 90 天。这是 GitHub artifact 服务提供的写入后不可修改属性，不是永久保存或防删除；正式 Release 附件负责更长期分发。dry-run 同样生成完整证明与验证 artifact，另保留可离线核验的 OCI tar 3 天，不登录 registry、不推送镜像、不创建正式 Release 或 tag、不触发通知。

这些记录及 BuildKit 原生 provenance 均未签名，依赖可信 Actions 控制面、内容寻址校验和不可覆盖 artifact 运输。它们不宣称是 GitHub artifact attestation、Sigstore 签名或 SLSA 高等级证明，不能凭 JSON 中的自述身份验证恶意构建者。本任务选择计划允许的 provenance 路径，保持现有权限；若维护者另要求 OIDC 签名，须按计划 §6.4 先授权新增的 id-token/attestations 写权限。

官方流程依据：[Docker attestation 运输](https://docs.docker.com/build/metadata/attestations/)、[Docker SBOM](https://docs.docker.com/build/metadata/attestations/sbom/)、[ORAS OCI tar 复制](https://oras.land/docs/commands/oras_cp/)、[Syft 1.54.1](https://github.com/anchore/syft/releases/tag/v1.54.1)、[ORAS 1.3.4](https://github.com/oras-project/oras/releases/tag/v1.3.4)。
